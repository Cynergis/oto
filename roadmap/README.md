# The OTO roadmap, as a work project

This folder is an OTO project that tracks [the roadmap](archive/OTO%20Roadmap%202.0.md) with the
work and communication packs: fourteen epics as work items, six phases as milestones, and every
change of state a dated, attributed fact. It is the first real use of Epic M and N, and the test
the roadmap asked for: if keeping it current is a chore, the model is wrong, and this is where
that shows.

`tests/test_roadmap_project.py` builds it from what is committed and checks that its states come
from transitions and events alone, that what shipped is deployed by the pull request that merged
it, and that the published copy is publishable.

## What is here

| Path | What it is |
|---|---|
| `graph.json` | the facts: the epics, the phases, the person the roadmap belongs to, every transition and message |
| `assertions.jsonl`, `changelog.jsonl` | what was said and who applied what; the engine appends, nobody edits |
| `audit.jsonl` | one hash-chained record per write since 2026-10-25, refusals included; `oto audit verify` proves it, `oto audit for <item>` reads it |
| `archive/`, `runs/`, `build/documents/` | the roadmap document as it arrived, the run that read it, and the corpus the facts quote (committed, as in repository mode: it is an input) |
| `ontology.config.json`, `rules.json`, `questions.json` | the `communication` ontology as installed (on `work`, `software-architecture`, `product`, `portfolio`) |
| the rest of `build/` | generated by `oto build`, not tracked |

## How we keep it current

Every command appends a fact and runs the gates; then `oto build --project roadmap`, and commit
`roadmap/` with the change that caused it. The state of an epic is never written on it.

**A pull request merges.** Its epic is deployed by the event, once; later pull requests for the
same epic change nothing:

```bash
oto work event merged-pr --repo Cynergis/oto --number 61 --item "Epic A" --environment prod --at 2026-10-27 --project roadmap
```

**An epic blocks on a decision or a person.** The block carries its reason and whom it waits on;
`notify` tells them, with the block's context, and their next session opens with it:

```bash
oto work set "Epic C" --state blocked --reason "the first Postgres connector: AGE, or SQL/PGQ?" --waiting-on "Chiheb Dkhil" --at 2026-10-27 --project roadmap
oto work notify "Epic C" --due 2026-10-31 --body "Which one?" --at 2026-10-27 --project roadmap
```

**The answer arrives.** A reply that resolves the message lifts the block in the same change:

```bash
oto work inbox --project roadmap
oto work reply message.epic-c-1 --resolve --body "SQL/PGQ where the version allows it; AGE otherwise." --at 2026-10-28 --project roadmap
```

**Where are we.** `oto work board --project roadmap`, or the Work tab of the workbench
(`oto serve --project roadmap --http 8790 --view workbench`); `oto query --project roadmap ask WK13
ITEM=workitem.epic-c` for one epic's current state and who set it, and `oto query entity
<transition> --as-of <date>` for what it was on a date.

`--by` is your git identity (`user.name <user.email>`); the inbox finds your Person by the email
recorded on it, else by name. `deployed` cannot be set by hand: only an event sets it.

## What is deliberately not here yet

Identity beyond git, the audit log, automatic status from factory events, reminders: phases 3, 5
and 6 of the roadmap. Until then this project is for the people in the repository.
